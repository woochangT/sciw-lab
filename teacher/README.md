# 교사용 화면과 인증 준비

저장소 루트에서 `python3 -m http.server 8765` 후 `http://localhost:8765/` 또는 각 미션 시작 화면에서 **교사용 대시보드 예시 보기**를 누른다. 직접 주소는 `http://localhost:8765/teacher.html`이다. 예시는 실제 교사 로그인이나 실제 학생 기록이 아니며, 시작 화면으로 돌아가 다시 들어올 수 있다. 기본값은 네트워크를 쓰지 않는 합성 데이터다. 같은 출처의 학생 게임을 `API_URL: ''`로 실행하면 같은 브라우저의 로컬 기록을 볼 수 있다. 현재 미션 01 설정은 기존 서버 주소를 가리키므로 합성 실험은 별도의 임시 복사본에서 URL을 비워야 한다. 로컬 기록은 기기 간 공유되지 않는다.

교사 화면의 새 수업 ID 생성은 암호학적 난수로 ID를 만든다. 이 ID는 자동으로 서버에 등록되지 않으므로 관리자가 접근 권한에 등록한 뒤 참여자에게 전달해야 한다. 같은 ID를 재사용하지 않는다. 기존 ID 없는 기록은 새 수업에 자동 편입되지 않는다.

20초마다 다시 조회하는 폴링이며 푸시가 아니다. 조회 오류가 나면 같은 반과 미션의 마지막 성공 결과를 남기고 다음 주기에 재시도한다. 반·미션·데이터 출처가 바뀌면 기존 결과를 지운다. 학생 화면에는 로컬 저장, 서버 저장 대기·실패·재시도 상태가 나타난다. 브라우저 저장 자체가 불가능하면 대기 기록도 보관되지 않을 수 있다.

## 서버 연결 상태와 반드시 필요한 작업

**이 저장소의 원격 연결은 인증 어댑터 계약까지 구현한 개발용 초안이며 실제 인증·배포 전에는 작동하지 않는다.** `authenticate_`는 어떤 credential도 거절한다. 서버는 학생 쓰기 및 교사 조회를 인증 전 차단한다. 기존에 이미 배포된 Apps Script에는 이 변경이 적용되지 않으며 기존 공개 조회나 쓰기가 여전히 작동할 수 있다. 운영자가 기존 배포를 별도로 확인해야 한다. 새 배포, 계정 설정, 권한 변경 및 실제 학생 데이터 접근은 수행하지 않았다.

운영 전 담당자가 다음 작업을 설계·구현·검증해야 한다.

1. 교사와 학생의 신원 제공자를 선택하고 가입·로그인 및 개인정보 처리 방식을 확정한다. `authenticate_(credential)`은 검증된 불변 사용자 ID `sub`를 반환해야 한다. 토큰 서명·발급자·대상·만료를 서버에서 검증하고 실패 시 거절한다. Google ID 토큰을 선택한다면 [Google 검증 지침](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)을 따른다. `tokeninfo`는 Google이 디버깅 용도로만 권고하므로 운영 검증기로 쓰지 않는다.
2. 교사 브라우저에 `window.SCIW_TEACHER_AUTH.signIn()`을 연결해 credential을 반환한다. 학생 브라우저에는 `window.SCIW_AUTH.getCredential()`을 연결한다. credential은 큐나 URL에 넣지 않고 메모리에서 POST 본문으로만 전달한다. 예제 토큰, 관리자 비밀키, 실제 credential을 정적 파일이나 Git에 넣지 않는다. 로그인 만료·로그아웃 및 토큰 갱신 처리도 구현한다.
3. Script Properties에 `ACCESS_GRANTS`를 관리자가 설정한다. 키는 인증 검증기가 반환한 불변 `sub`이며 예시는 다음과 같다. 실제 인원 배정, 변경·회수와 보관 기간 관리를 따로 마련해야 한다.

   ```json
   {"teacher-sub":{"teachers":[{"classCode":"A","missionId":"m02","lessonId":"L_example"}]},"student-sub":{"students":[{"classCode":"A","missionId":"m02","lessonId":"L_example","studentNo":"1"}]}}
   ```

4. 별도 테스트용 스프레드시트와 Apps Script 배포에서 `teacher/config.js`의 공개 `API_URL`을 지정하고, 두 학생 설정의 `API_URL`도 테스트 배포로 연결한다. HTTPS, 실제 배포의 리디렉션·CORS·인증, 여러 기기, 만료·회수, 실패·재전송 및 과도한 요청을 검증한다. 그 후에만 운영 배포를 별도로 결정한다.
5. 서버의 요청·필드·구조 크기 제한과 수업별 권한 분리는 구현되어 있다. 운영 전에는 악의적인 대량 요청 방지, 서버 측 수업 등록·종료와 명단 관리, 데이터 보존·삭제 정책 및 보안 검토가 추가로 필요하다. 수업 ID는 재사용하지 않아야 하며 권한 정보는 현재 수동 설정에 의존한다.
6. 서버에는 버전이 있는 미션별 고정 평가 항목이 있으나 서버 판정기는 아직 없다. 클라이언트가 보낸 판정은 검증되지 않은 참고 기록으로만 저장하며 서버 평가 열로 변환하지 않는다. 교사 화면에서 확정 점수나 성취 판단에 쓰면 안 된다. 기존 `judge` 엔드포인트는 차단되어 있다. 운영에서 자동 판정을 쓰려면 고정 루브릭을 적용하는 서버 판정기와 검증이 별도로 필요하다.

서버 요청은 반·미션·수업 ID별 교사 권한과 학생의 반·미션·수업 ID·번호 권한을 각각 확인하고 기존 세션의 소유자와 소속 변경을 거절한다. 이 모델은 인증 구현이 올바르다는 전제에서만 유효하다. 학생 권한을 세션별로 더 세분화하거나 명단의 번호 변경·중복 문제를 처리하는 작업도 필요하다. 배치 중 일부만 저장되고 실패할 수 있으므로 재시도는 기존 시도 ID로 중복을 막는다. 인증 없는 시트 직접 접근이나 기존 배포 접근은 이 코드가 통제하지 못한다.

## 테스트

`node --test teacher/tests/*.cjs '감자 삼투/web/tests/'*.cjs '강철솜 질량 보존/web/tests/'*.cjs`

모의 인증과 Apps Script 모의 저장소를 사용한다. 실제 Google 인증, Apps Script 배포, 스프레드시트, 브라우저 렌더링이나 네트워크 동작을 검증한 것은 아니다.
